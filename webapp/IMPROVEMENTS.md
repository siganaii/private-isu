# private-isu 改善まとめ（Go 実装）

最終更新: 2026-10-11

## 概要

- 実装を Ruby から **Go**（`webapp/golang/`）に切り替えてチューニングした
- 計測は docker compose で行い、本番（c7a.large: 2 vCPU / 4GB）に近い CPU 割り当てにしている
- 初期状態（Ruby）のスコアは **1,275**。現在（B+E 版）は **約 137 万**（2026-10-11、3回平均 1,371,682。範囲 1,352,019〜1,405,352）

> 注意: 手元の環境では、同じコードでも日によってスコアが約2割変わる。途中で CPU の割り当ても変えているので、スコアは同じ期間・同じ日の計測同士でのみ比べている（「5. スコアの推移」を参照）。

## 1. 計測環境の整備


| 項目 | 内容 |
| --- | --- |
| CPU 割り当て（`compose.override.yml`） | app・mysql・nginx・memcached が CPU 0,1 の2コアを共有する（本番の「全プロセスを1台に同居」に合わせた）。ベンチマーカーは別サーバーの想定で CPU 4〜7 に置く |
| ベンチ実行スクリプト（`bench.sh`） | `./bench.sh quick`: 負荷20秒を1回（fail の確認用）。`./bench.sh [N]`: 本計測を N 回（既定3回）、30秒間隔で実行して平均を出す |
| alp 用ログ（`etc/nginx/conf.d/00-alp-log.conf`） | LTSV 形式のアクセスログ。ベンチを回すたびにログを空にする |
| pprof | アプリの `:6060` で取得できる（Docker ネットワーク内からのみ） |

計測の運用ルール:
- 1回ごとの揺れが大きいので、各計測の間に30秒あける
- コンテナ起動直後の1回目はスコアが大きく下がるため、`quick` を1回回して温めてから本計測する
- ベンチは並列で実行しない（CPU を取り合ううえ、`/initialize` で互いのデータを消してしまう）

## 2. アプリケーション（`golang/app.go`）

### 画像を DB からファイルへ移した
- 投稿された画像は `public/image/{id}.{ext}` に書き出すだけにし、DB には入れない（`imgdata` は空文字）。画像入りの INSERT は1回 30ms 以上かかっていた
- 初期データの画像は、最初にアクセスされたときにアプリがファイルに書き出す。2回目からは nginx が直接返す
- ファイルは一時ファイルに書いてから rename する（nginx が書きかけのファイルを返さないため）
- `/initialize` で、ベンチ中に追加された画像（id > 10000）のファイルを消す

### DB のデータをメモリにキャッシュして N+1 を解消した
| キャッシュ | 中身 | 更新するタイミング |
| --- | --- | --- |
| `usersCache` | users の全件 | 登録・BAN・`/initialize` |
| `commentsCache` | 投稿ごとのコメント全件（件数・最新3件を返す） | コメント投稿・`/initialize` |
| `postsCache` | posts の全件（画像を除く。作成日時順に並べて持つ） | 投稿・`/initialize` |

- タイムライン・投稿詳細・ユーザーページは DB に問い合わせずに組み立てる
- 「コメント件数と最新3件」を取るクエリが MySQL の処理時間の約3割を占めていたが、これがなくなった

### その他のアプリの改善
- **インデックス**: `/initialize` で、無ければ作る
  - `comments (post_id, created_at)`、`comments (user_id)`
  - `posts (created_at)`、`posts (user_id, created_at)`
- **パスワードハッシュ**: `bash`・`openssl`・`sed` のプロセス起動をやめ、Go の `crypto/sha512` で計算する（ログイン1回で6プロセス起動していた）
- **画像の BLOB を読まない**: 画像以外が必要なクエリでは `imgdata` を SELECT しない
- **テンプレートのパースを起動時の1回に**
- **投稿1件分の HTML は手書き**（`writePost`）。一覧では投稿・コメントの数だけ描画するので、ここだけ html/template を使わない。ページ全体はテンプレートのまま（全部を手書きにした D は不採用）
- **BAN**: 選ばれたユーザーを `WHERE id IN (...)` の1回の UPDATE でまとめて更新する
- **DB 接続**:
  - `InterpolateParams=true` でプレースホルダをクライアント側で展開し、PREPARE の往復をなくした
  - コネクションプールを広げた（MaxOpen/MaxIdle を 64、ConnMaxLifetime を1分）

### A'. GC の頻度を下げた（+9%）
- GC が CPU の 17% を使っていた
- `debug.SetGCPercent(400)` と `debug.SetMemoryLimit(300MiB)` を設定した
- 上限を 600MiB にした版（A）は +4% にとどまった。コンテナのメモリ上限（1GiB）にページキャッシュも含まれ、メモリの回収が頻発したため

### B. セッションをアプリのメモリに持つようにした（+6%）
- memcached を使う `gorilla-sessions-memcache` は、通信・Cookie の署名検証（HMAC）・gob の変換で、アプリの CPU の約2割を使っていた
- `sessions.Store` を実装した `memorySessionStore` に置き換えた。Cookie にはランダムなセッション ID だけを入れる。ハンドラは変更していない
- アプリは1プロセスなので、メモリに持っても食い違いは起きない。ただし再起動するとログイン状態は消える
- memcached は使わなくなったが、コンテナは残っている

### D. html/template をやめて HTML を全部手書きにした（不採用）
- html/template のリフレクションと文脈ごとのエスケープが、CPU の1割強を占めていた
- `writeLayoutHeader` / `writeLayoutFooter` / `writePosts` / `writeAccountForm` などで全ページを組み立て、`sync.Pool` で `bytes.Buffer` を使い回す実装にした。13ページで変更前と HTML を比べ、空白以外に差がないことも確認した
- しかし B 版との交互計測で効果を確認できず（D の平均の方が低かった。「5. スコアの推移」を参照）、コード量が増えるだけなので外した
- 一度コミット（087739d）に入っていたが、B+E 版で元に戻した

### E. 投稿画像を `io.ReadAll` で読み込まない（採用。効果は揺れの範囲）
- `postIndex` で画像を `io.ReadAll` で `[]byte` に読み込んでから書き出していた。投稿のたびに 1MB 前後のメモリを確保していた
- `writeImageFile` が `io.Reader` を受け取るようにし、multipart のデータから画像ファイルへ `io.Copy` で直接書き出す
- サイズの上限チェックは、読み込んだバイト数ではなく multipart のヘッダー（`header.Size`）で行う
- 投稿した画像が元のファイルとバイト単位で一致することを確認した
- 投稿はリクエスト全体のごく一部なので、スコアの差ははっきりしない。悪化の兆候はなく、変更も小さいので採用した

## 3. nginx

| 設定 | 理由 |
| --- | --- |
| `/image/` は `try_files $uri @app` | 画像ファイルがあれば nginx が返し、無ければアプリに回す |
| 静的ファイル・画像に `expires 1d` | ブラウザにキャッシュさせて 304 で済ませる |
| `open_file_cache`（`open_file_cache_errors off`） | open/stat の結果を使い回す。「ファイルが無い」は覚えない（覚えると投稿直後の画像が最大30秒アプリに回る） |
| `upstream` で `keepalive 64` | アプリへの接続を使い回す。毎回つなぐと TIME_WAIT が溜まって 502 になっていた |
| `client_body_buffer_size 2m` | 投稿画像を一時ファイルに書かず、メモリで受け取る |
| `worker_connections 8192`、`worker_rlimit_nofile 65536` | 既定の 1024 では "worker_connections are not enough" が出ていた |
| `keepalive_timeout 5` | ベンチマーカーは接続を閉じずに捨てるため、既定の 65 秒だとベンチマーカー側のポートが枯渇していた |
| C. 画像・静的ファイルの `access_log off`（+1%） | 1回の計測で約105万件のログを書いており、LTSV の組み立てに CPU を使っていた。alp で見たいのは動的ページだけ |
| 既定の access.log を無効にした | 計測用の alp ログだけを出す |

> nginx.conf は単一ファイルの bind mount なので、編集したら `docker compose up -d --force-recreate nginx` で反映する（reload では反映されない）。

## 4. MySQL（`etc/mysql/conf.d/isuconp.cnf`）

| 設定 | 理由 |
| --- | --- |
| `innodb_buffer_pool_size = 256M` | コンテナのメモリ上限が 1GB なので抑えた。よく読むのは comments とインデックスくらいで小さい |
| `innodb_flush_log_at_trx_commit = 2` | コミットのたびに fsync しない（OS がクラッシュすると最大1秒分の更新を失う可能性がある） |
| `disable-log-bin` | レプリケーションしないのでバイナリログは不要 |

## 5. スコアの推移

途中で計測環境（CPU の割り当て）を2回変えている。スコアを比べられるのは同じ期間の中だけ。

### 期間1: 2026-10-04（CPU 割り当ての固定なし。app と mysql は上限1コア）

| # | 変更 | スコア |
| --- | --- | ---: |
| 0 | 初期状態（Ruby） | 1,275 |
| 1 | Go 実装に切り替え | 2,082 |
| 2 | `comments (post_id, created_at)` にインデックス（後に `/initialize` で作るように変更） | 21,416 |
| 3 | トップページのクエリ修正（users を JOIN して `del_flg = 0` で絞り `LIMIT 20`、`posts (created_at)` にインデックス）+ `InterpolateParams` | 26,499 |
| 4 | 画像をファイルに書き出し、nginx から直接返す | 61,117 / 62,341 |
| 5 | `makePosts` の N+1 を解消（`IN` / `GROUP BY` / `ROW_NUMBER()` で、投稿数に関係なく4クエリに） | 105,664 |
| 6 | テンプレートのパースを起動時の1回だけに | 113,076 |
| 7 | パスワードハッシュを Go で計算（`bash`・`openssl`・`sed` のプロセス起動をやめた）+ 静的ファイルを nginx から返す | 247,472 |

- #3 の直前は 20,395（#2 と同じ状態）。#3 は、その数字との比較
- #7: pprof には外部プロセスの CPU が出ないため、ハッシュ計算は 3.7% にしか見えていなかったが、実際には大きな負担だった

### 期間2: 2026-10-05（途中から CPU 割り当てを固定: app=0、mysql=1、nginx=2〜3、ベンチマーカー=4〜7）

| 変更 | スコア |
| --- | ---: |
| 開始時（期間1の #7 と同じコード） | 201,890 / 221,301 |
| DB のコネクションプール、`/posts/{id}` で画像 BLOB を読まない、`comments (user_id)`・`posts (user_id, created_at)` にインデックス、`/@{accountName}` に `LIMIT 20` を付け件数を数えるクエリを2本にまとめた、一覧クエリにインデックスヒント、MySQL の設定（binlog 無効・`flush_log_at_trx_commit=2`・buffer pool 256MB）、nginx の upstream keepalive | 385,083 / 276,950 |
| ↑ と同じコードで、CPU 割り当ての固定 + 各計測の間に30秒の休止 | 中央値 471,000 |
| 投稿1件分の HTML を手書き（`writePost`）+ `usersCache` | 平均 624,738（677,187 / 609,812 / 587,216） |

途中で起きた問題:
- `posts (user_id, ...)` を追加したら、トップページのクエリの実行計画が悪化した（0.9ms → 291ms、スコアが約5万に低下）。インデックスヒント（`FORCE INDEX`・`STRAIGHT_JOIN`）で計画を固定して解決した。このヒントは、後に `postsCache` で一覧のクエリ自体がなくなったため削除した
- アプリが速くなった結果、nginx → アプリの接続でポートが枯渇して 502 が出た。upstream keepalive で解決した
- buffer pool 512MB では、MySQL がメモリ上限（1GB）に1万回以上当たっていた。256MB に下げると0回になり、スコアも下がらなかった

| # | 変更 | スコア（平均） |
| --- | --- | ---: |
| — | 開始時 | 約 664,000（612,176 / 715,160） |

| 4 | nginx の調整（既定 access.log の停止、`open_file_cache`、`worker_connections`、`keepalive_timeout 5`） | 1,327,596 |

- #1 の最初の実装では、画像ファイルを書き終える前に投稿がタイムラインに出て、画像が 404 になっていた（fail 28〜46件）。INSERT・ファイルの書き出し・コミットを1つのトランザクションにまとめて解決した

### 期間4: 2026-10-09 以降（本番寄りの割り当て）

改善 A〜E の各段階（同じ日の計測、3回平均）:

| 段階 | スコア | 前の段階との差 |
| --- | ---: | ---: |
| A なし（期間3の #4 と同じコード） | 982,736 | — |

D の効果を確かめるため、同じ日に B 版と D 版を交互に計測した（B→D→D→B→B→D）:

| 版 | 1回目 | 2回目 | 3回目 | 平均 |
| --- | ---: | ---: | ---: | ---: |
| B | 1,262,477 | 1,061,790 | 1,254,423 | 1,192,897 |
| D | 1,104,944 | 1,255,670 | 879,404 | 1,080,006 |

1回ごとの揺れ（約88万〜126万）が版の差より大きく、D が効いたかどうかは判定できなかった。そのため D は外した。

E は D を外した B 版の上に実装し、同じ日に B 版と B+E 版を交互に計測した（B→BE→BE→B→B→BE）。その後、リポジトリを B+E 版にして本計測を3回行った:

| 版 | スコア | 平均 |
| --- | --- | ---: |
| B | 814,678 / 1,354,590 / 1,295,902 | 1,155,057 |
| B+E（交互計測） | 1,219,960 / 1,378,274 / 1,369,799 | 1,322,678 |
| B+E（本計測） | 1,405,352 / 1,352,019 / 1,357,675 | **1,371,682** |

- B の1回目（81万）はその日最初の計測で、温め用の quick を回した後でも低かった。これを除くと B の平均は 1,325,246
- B+E は6回中5回が135万以上で、B の最高（135万）を下回らなかった。ただし差は数%程度で、揺れの範囲とも言える

## 7. 気になっている点

- 改善の前から、app コンテナがメモリ上限（1GiB）に数千回当たっている。投稿画像のページキャッシュが原因。手元の制限によるもので、本番（4GB）では起きにくいと考えている
- ベンチ中に VS Code のサーバー（node）が CPU を約 0.9〜1.3 コア使っている。画像ディレクトリを監視対象から外したが、原因はまだ分かっていない
- 手元で効いた改善が本番でも効くとは限らない
